## Chapter 5 — Input Data Formats

The software pipeline requires a standardized set of input file formats to begin processing the survey data. While the drone captures raw proprietary data, this is typically pre-processed via DJI Terra to produce standard industry formats. The application relies on these specific formats to ensure broad compatibility and robust data handling.

### 1. RGB Imagery (.JPG)

* **Format:** Standard JPEG format.
* **Usage:** Used for semantic AI object detection (RF-DETR/SAM 2), manual user review within the UI, and projection mapping.
* **Requirements:** Images must contain complete EXIF and XMP metadata, specifically including GPS coordinates, altitude (Absolute and Relative), and gimbal orientation (Yaw, Pitch, Roll). The software will extract this metadata during the initial ingestion phase to populate the spatial database.

### 2. LiDAR Point Clouds (.LAS / .LAZ)

* **Format:**
  * **LAS:** The industry-standard binary format for storing 3-dimensional point cloud data (developed by ASPRS).
  * **LAZ:** The compressed version of LAS. It provides lossless compression, drastically reducing file sizes (often by 70-80%) which is critical for large corridor surveys.
* **Usage:** The absolute geometric source of truth. Used for clearance calculations, elevation profiling, object boundary extraction, and conductor sag analysis.
* **Requirements:** The point clouds should ideally be colorized (RGB values mapped to points) and contain Intensity, Return Number, and proper GPS Time attributes. The system will primarily utilize LAZ formats to optimize disk I/O and storage.

### 3. Trajectory Files (.TXT / .CSV / .OUT)

* **Format:** Plain text or CSV files containing time-series data.
* **Usage:** Maps the exact path of the drone. Used by advanced LiDAR processing algorithms to calculate scan angles, optimize point cloud tiling, and verify flight continuity.
* **Requirements:** Must contain columns for GPS Time, Easting/Longitude, Northing/Latitude, Elevation, Roll, Pitch, and Heading. Standard formats output by POSPac or DJI Terra are supported.

### 4. Camera Pose Files

* **Format:** Standardized CSV or text files (often generated by photogrammetry software during aerial triangulation).
* **Usage:** Provides the refined, highly accurate extrinsic parameters (X, Y, Z, Omega, Phi, Kappa) for every image.
* **Requirements:** While basic EXIF data provides initial estimates, a dedicated pose file is heavily preferred for precise mathematical projection between the 2D image plane and the 3D LiDAR space. This ensures tight alignment during the RGB-LiDAR fusion phase.

### 5. Digital Surface Models (DSM) — *Optional*

* **Format:** GeoTIFF (.tif)
* **Usage:** A rasterized representation of the highest elevations (including trees, buildings, and infrastructure). It is utilized to quickly estimate object heights without querying the raw point cloud and to provide a base layer for the 2D Map Workspace.
* **Requirements:** Must be properly georeferenced to the project's coordinate system.

### 6. Digital Terrain Models (DTM) — *Optional*

* **Format:** GeoTIFF (.tif)
* **Usage:** A rasterized representation of the bare earth (with trees, buildings, etc., mathematically removed). Crucial for calculating true ground clearances (e.g., the distance from a conductor down to the bare earth, rather than to the top of a tree).
* **Requirements:** Like the DSM, must be correctly georeferenced.

### 7. Orthomosaics — *Optional*

* **Format:** GeoTIFF (.tif) or Cloud Optimized GeoTIFF (COG)
* **Usage:** A 2D georeferenced composite map created by stitching the RGB images together and correcting for perspective distortion. It serves as the primary high-resolution background map in the User Interface.
* **Requirements:** Given the massive size of corridor orthomosaics, the software heavily relies on the COG format or pre-tiled structures (like XYZ tiles) to allow for efficient lazy-loading and streaming in the frontend map component.
